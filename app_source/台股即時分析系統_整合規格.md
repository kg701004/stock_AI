# 台股即時分析與決策支援系統：整合規格（重新審視版）

> 目標：建立 Windows 桌面版「台股即時監控、分析與決策支援」工具。
> 
> 範圍原則：V1 僅提供分析、預警、回測與模擬交易；不含自動下單，也不在行情模組中放置任何下單程式碼。

## 1. 一句話定位

這不是「預測必漲跌」的軟體，而是一套可追溯、可回測的決策支援系統：它根據當時可取得的資料，輸出條件、機率、風險與理由，並持續驗證其後續表現。

目前資料範圍限定為：**免申請、免付費的公開盤後資料與手動匯入檔案**；不使用券商 API、即時 WebSocket、帳戶憑證或付費行情。

## 2. 核心設計原則

1. **可驗證優先**：每個訊號、模型預測與警示，都必須保存輸入資料版本、時間戳、規則／模型版本、理由與事後結果。
2. **資料時間正確**：同時保存交易所時間、資料發布時間與本機接收時間；禁止使用交易當下尚未公開的資料。
3. **規則與模型分工**：規則引擎負責風險閘門與可解釋訊號；機器學習只輸出經驗證的機率或區間，不直接輸出買賣命令。
4. **市場狀態優先**：先判定多頭、震盪、空頭或高波動，再決定可使用的策略、門檻與部位上限。
5. **分層資料來源**：券商 WebSocket 處理盤中行情；TWSE／TPEx／TAIFEX 等公開資料補充盤後、法人、基本面與衍生商品資料。
6. **安全預設**：分析模式預設啟用；自動交易預設永久關閉，只有模擬交易可進入後續版本。

## 3. 使用者可看見的輸出

### 3.1 即時自選股與圖表

- 自選股：代號、名稱、現價、漲跌、漲跌幅、開高低、昨收、成交量、五檔、最後更新時間與連線狀態。
- 圖表：1 分、5 分、日 K；成交量；SMA／EMA、VWAP、RSI、MACD、布林通道。KD 可列為後續選配，避免 V1 指標過多。
- 資料品質：顯示資料延遲、是否過期、來源、整股／零股交易別與市場狀態。

### 3.2 掃描、判斷與風險說明

掃描器可偵測突破昨高或區間高點、相對量放大、價格位於 VWAP 上方、均線趨勢、急漲、爆量不漲等條件。

每筆結果必須輸出：

- 分數與分級：強勢觀察／偏多觀察／中性／偏弱／高風險。
- 成立理由與實際輸入值，例如「5 分鐘相對成交量 2.4 倍」。
- 反向風險，例如乖離過大、接近壓力、流動性不足或大盤轉弱。
- 資料時間與規則版本。

建議初始評分權重：趨勢 25、動能 20、成交量 20、突破型態 15、市場環境 10、風險扣分最多 10。權重不是常數；完成績效統計後，才可依市場狀態調整。

### 3.3 機率預測（V1 後段才啟用）

可先定義而不急於部署的三種目標：

1. **方向分類**：未來 30 分鐘上漲超過 0.5%、震盪或下跌超過 0.5% 的機率。
2. **事件機率**：未來 30 分鐘是否先上漲 1% 再下跌 0.5%；此類標籤較貼近報酬風險。
3. **報酬／區間**：未來 5 或 30 分鐘預期報酬與預測區間。

畫面應呈現「上漲機率、下跌機率、區間、可信度與失效條件」，不可宣稱保證獲利或必定到價。

```text
│  ├─ pipeline/        # queue、去重、過期檢查、K 線聚合
│  ├─ analysis/        # 指標、規則引擎、掃描、market regime
│  ├─ storage/         # SQLite schema、repository、批次寫入
│  ├─ backtest/        # 回放、成本、績效、walk-forward
│  ├─ ml/              # 特徵、標籤、訓練、校準、推論（後期）

├─ data/
├─ logs/
└─ tests/
```

### 架構不可違反的規則

- 所有行情供應商都實作同一個 `BaseMarketDataProvider`：`connect`、`disconnect`、`subscribe`、`unsubscribe`、`get_snapshot`、`get_history`。
- UI 不可直接呼叫 API 或 SQLite；券商 callback 也不可直接操作 GUI。
- 資料流固定為：WebSocket／Mock → Queue → 驗證與聚合 → 分析 → Qt Signal → UI；SQLite 採 100–500 ms 的批次寫入。
- 資料模型採 immutable dataclass，驗證股票代號、價格與成交量；拒絕重複、亂序或過期 Tick。
- API 金鑰只可從 `.env` 讀取，`.env` 不可提交版本控制。

## 5. 最小資料庫與資料治理

V1 建議資料表：`symbols`、`ticks`、`candles`、`signals`、`alerts`、`scan_results`、`system_events`、`strategy_runs`、`backtest_trades`、`model_predictions`。

所有決策相關資料至少要有：`symbol`、`event_time`、`received_time`、`source`、`data_version`、`strategy_or_model_version`。`signals` 額外保存 `score`、`confidence`、`reason_json`、`risk_json`；`model_predictions` 保存預測期限、類別機率、特徵版本、校準版本與事後標籤。

資料品質檢查必須涵蓋：缺值、重複、時間倒退、盤別錯置、整股／零股混用、公司行動調整、停牌與漲跌停情境。盤後資料需保存「公布時間」，不能以資料日期取代可交易時間。

## 6. 策略與回測的必要條件

任何訊號都必須可回答：「過去在相同市場狀態下出現多少次、後續 1／3／5／10／20 日的勝率、平均報酬、最大有利變動（MFE）、最大不利變動（MAE）各是多少？」

回測必備：

- 時序切分與 walk-forward 驗證，不可隨機切分時序資料。
- 手續費折扣、最低手續費、證交稅、ETF／個股差異、滑價、買賣價差、部分成交與流動性限制。
- 漲跌停買不到／賣不掉、跳空、停牌、除權息、分割、減資與現金增資處理。
- 當時的股票池，避免存活者偏差與選股池洩漏。
- 訓練、驗證、樣本外、模擬盤及影子測試紀錄分開保存。

## 7. 缺口盤點與優先順序

### P0：先完成，否則不可依訊號進行投資決策

1. SQLite 歷史資料與完整時間戳／發布時間。
2. 訊號產生、事後結果與績效閉環。
3. 市場狀態模型與策略啟用／停用規則。
4. 有交易成本、滑價與可成交性限制的 walk-forward 回測。
5. 組合層風控：單筆風險、單股／產業曝險、相關性、最大回撤與連續虧損降槓桿。
6. 影子測試：每天保存當時資料、訊號、版本與後續結果。

### P1：明顯提升中短期判斷品質

- 市場廣度：漲跌家數、新高新低、站上均線比例、上市／上櫃與大小型股強弱。
- 產業輪動：產業相對強弱、成交金額占比、產業法人與營收動能。
- 基本面與事件：月營收、財報、獲利品質、估值、法說會與重大訊息；特別區分「好消息」與「優於預期」。
- 台指期：日夜盤、基差、未平倉量、近遠月轉倉與法人多空的變化，不只看淨口數。
- 選擇權：Put/Call 比、未平倉量、隱含波動率、偏斜、期限結構與結算效應。
- 動態風控：ATR、支撐壓力與市場狀態決定停損、停利與部位，而不是固定百分比。

### P2：資料與工程成熟後再做（目前不納入）

- 五檔／逐筆委託簿、訂單流不平衡、撤單速度與交易成本模型（需要即時授權行情）。
- 新聞 NLP、重大事件去重與供應鏈知識圖譜。
- Logistic Regression 基準、LightGBM／XGBoost、機率校準、模型漂移監控與多模型融合。

## 8. 機器學習上線門檻

先以 Logistic Regression、簡單均線規則及「永遠看多」等基準比較；之後才考慮 LightGBM 或 XGBoost。模型不可只報 accuracy，還需至少報告：樣本外績效、交易後報酬、最大回撤、Brier score、log loss、calibration curve，並按股票、預測期限與市場狀態拆分檢查。

若模型未能在樣本外、含成本條件下穩定優於簡單基準，就不部署為決策因子。大型語言模型僅用於解釋、摘要與新聞輔助，不參與逐筆 Tick 的即時交易決策。

## 10. 重新審視結論

原始構想的強項是已涵蓋即時行情、技術分析、警示、回測、模擬交易與 AI 的完整藍圖；最大風險則是把太多資料來源、指標、預測功能同時放入第一版，導致沒有一個訊號能被可靠驗證。

因此最正確的開發順序是：**先讓資料與訊號可保存、可重播、可驗證，再擴大資料面與模型複雜度。** 最近期的第一個實作任務應是 V0.1：以 Mock 行情完成端到端資料流與測試，而不是直接串券商 API 或訓練 AI。
